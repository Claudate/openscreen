## 0. 一句话结论（给决策层）

**语义元素缩放是 Cap 对标 Screen Studio 的真正护城河——因为 Screen Studio 架构上根本没接无障碍树（纯光标驱动），而 Cap 启动就硬依赖辅助功能权限、且摄像头模块已内置 ONNX Runtime。结论：推荐「AX 无障碍优先 + 视觉/坐标兜底」的混合渐进路线，第一阶段（纯 AX，原生应用精准贴合控件）工作量约 3-5 人日、零新增权限、零新增依赖、不碰渲染层，是性价比极高的差异化切入点。**

## 1. 为什么做这件事（差异化定位）

### 1.1 当前 Cap 自动聚焦的「最后一公里」缺陷

核对前任 P0 升级后的生成算法（`apps/desktop/src-tauri/src/recording.rs` 的 `generate_zoom_segments_from_clicks_impl`，L3071-3075 核心原则注释），现状是：

> 生成阶段只决定「何时聚焦 + 聚焦多少 + 怎么分段」，**焦点坐标交给渲染层 Auto 跟随逻辑**，故全程输出 `ZoomMode::Auto`，`moves` 仅用于聚类，**不输出坐标**。

> 术语澄清（与团队基线对齐）：**P0 的算法升级主体在 `recording.rs` 的生成函数**（点击聚类→分段→动态强度）；`crates/rendering/src/zoom_focus_interpolation.rs` 是**渲染层既有代码**（消费 `ZoomMode::Auto` 段做弹簧跟随插值），本报告引用它仅为说明"坐标在渲染层定"这一分层事实，非 P0 改动产物。

即：**缩放框的中心 = 渲染时跟随光标**。这够好，但有天花板——光标只是一个点，缩放框不知道用户真正在操作的「按钮 / 输入框 / 链接」的**真实边界**。表现为：放大后控件可能贴边、可能框得过大露出无关区域、可能框得过小切掉控件。

### 1.2 竞品真相（2026 联网核实，铁证）

| 来源 | 关键结论 |
|---|---|
| screenify.studio 技术拆解[1] | "Screen Studio **does not use UI element detection** to generate zooms... just clicks"——每次点击生成一个 zoom 关键帧 |
| GitHub `Screen-Studio-Effects` 算法逆向[3] | 实测算法仅 = `raw cursor events → shake filter → spring simulation → silence-based auto-zoom`，**纯光标+弹簧物理，无 AX/无视觉** |
| Screen Studio 用户社区[5] | 痛点：自动缩放"以光标点为锚"，且 hover/拖拽/菜单演示**不触发**缩放 |

> ★ **护城河逻辑**：Screen Studio 卖 $89-229 的杀手锏，本质是"光标点 + 弹簧动画"。Cap 已经拥有同级的弹簧渲染层（`zoom_focus_interpolation.rs`），若再叠加 **AX 拿到的真实控件矩形**，就能做出"缩放框自动精准贴合 UI 元素"的体验——**这是 Screen Studio 架构上做不到的**（它没接无障碍树）。这不是追赶，是超越点。

## 2. 三条技术路线对比（核心）

### 路线 A：macOS AX 无障碍树（Accessibility Tree）

**原理**：点击发生时，用屏幕坐标调 `AXUIElementCopyElementAtPosition(x, y)` 拿到该位置最顶层 UI 元素，读取它的 `AXFrame`（CGRect = 位置+尺寸）和 `AXRole`（按钮/文本框/链接…），得到**被操作控件的真实矩形**。

**Rust 生态（2026 已成熟，联网核实）**：

| 库 | 说明 |
|---|---|
| `objc2-application-services` | Apple 官方 objc2 系列，`AXUIElement::copy_element_at_position` |
| `accessibility-sys` / `accessibility-sys-ng` | C FFI 直绑，`AXUIElementCopyElementAtPosition` / `AXUIElementCopyAttributeValue` |
| `axuielement` v0.9.1 | 安全高层封装，含 `AXValue` 对 `CGRect` 的 round-trip + `SystemWideElement` 便捷查询 |

**✅ 决定性优势：零新增权限**（铁证 `apps/desktop/src-tauri/src/permissions.rs`）

```rust
// L43-46：Cap 已 link AX 无障碍 API
unsafe extern "C" { fn AXIsProcessTrusted() -> bool; ... }
// L445-447：辅助功能是 Cap 启动的【硬性必需】权限
pub fn necessary_granted(&self) -> bool {
    self.screen_recording.permitted() && self.accessibility.permitted()
}
```

> 用户为了用 Cap 录屏**本来就必须授予辅助功能权限**，而这正是 `AXUIElementCopyElementAtPosition` 所需的同一个权限。AX 方案最大的顾虑（权限摩擦）**直接清零**。

**⚠️ 致命盲区（2026 联网核实，必须如实记录）**：

| 应用类型 | AX 表现 | 录屏教程是否常见 |
|---|---|:---:|
| 原生 AppKit / SwiftUI（访达/系统设置/Xcode/Sketch） | ✅ 完整树，精确矩形+角色 | 中 |
| **Electron**（VS Code/Slack/Discord/Notion/Cursor 自身） | ❌ 默认"一片空 `AXGroup`"，无角色无可用边界 | **极高** |
| **浏览器内网页**（Chrome/Safari 里的 Web 应用） | ⚠️ 树存在但是 ARIA 派生的 `AXGroup` 汤，外部进程难用 | **极高** |
| **Metal/OpenGL canvas**（Figma 画布/游戏/PS 文档区） | ❌ 整窗口只有一个不透明元素 | 中高 |

> Electron 需 `app.accessibilitySupportEnabled=true` 或 `--force-renderer-accessibility` 才建树，但这是**被录制的目标应用**的设置，Cap 无法控制。结论：**AX 在视频创作者最常录的浏览器/Electron 场景里会大面积返回空**——这是 A 路线不能单独成立的根本原因。

**业界统一最佳实践（来源[2][4]）**：`AX-first, vision-fallback`——AX 拿得到就用（原生应用，精确快），AX 空了就降级。这直接指向路线 C。

| 维度 | 评价 |
|---|---|
| 精度 | 原生应用 ★★★★★（像素级真实矩形）；Electron/Web ★（失效） |
| 性能 | ★★★★★（单次 hit-test 微秒级，仅点击瞬间调一次，非逐帧） |
| 隐私 | ★★★★★（纯本地系统 API，零上传，AGPL 合规） |
| 工程量 | ★★★★（小，新增采集字段 + 生成算法消费） |
| 覆盖率 | ★★（受 Electron/Web 盲区拖累） |

### 路线 B：视觉检测（ONNX / YOLOv8）

**原理**：对录制画面跑 UI 元素检测模型（OmniParser 系：YOLOv8 Nano 检测可交互区域 → bbox），找出点击坐标命中的元素框。不依赖系统树，**纯像素**，因此**不受 Electron/Web 盲区影响**。

**✅ 重大发现：Cap 已内置 ONNX Runtime！**（铁证 `crates/camera-effects/Cargo.toml`）

```toml
# L17 (非macOS)  / L20 (macOS, 用 CoreML 加速!) / L23 (Windows, DirectML)
ort = { version = "2.0.0-rc.12", ..., features = [..., "coreml", "api-23"] }   # macOS
```

> Cap 用 `ort`(onnxruntime) 做摄像头背景分割，**macOS 走 CoreML 硬件加速**。这意味着视觉路线的 ONNX 基础设施**已经现成**，不必从零引入——B 路线的工程门槛因此大幅下降。

**模型现状（2026 联网核实，OmniParser V2）**：

| 项 | 数据 |
|---|---|
| 检测器 | YOLOv8 Nano（fine-tuned，约 6-12MB ONNX，可 Ultralytics 一键导出 ONNX） |
| 延迟 | **0.6s/帧 (A100) / 0.8s/帧 (单 4090)**——强 GPU 数据，普通 Mac 更慢 |
| License | `icon_detect` = **AGPL**（与 Cap 兼容，需开源）；`icon_caption` = MIT |
| 我们的简化空间 | **只需检测器拿 bbox**，不需要 caption/OCR（我们要矩形不要"按钮叫什么名"）→ 可只移植 YOLOv8 Nano，砍掉 Florence-2 + PaddleOCR |

**⚠️ 关键约束**：0.6-0.8s/帧 = **绝不可能录制时实时（60Hz）逐帧检测**，只能"点击瞬间截一帧 / 离线后处理特定帧"。好在我们的场景恰好只需在**点击时刻**检测一次（与点击聚类天然对齐），不需要逐帧。

| 维度 | 评价 |
|---|---|
| 精度 | ★★★（依赖模型，icon 检测准但偶有漏检/重复框） |
| 性能 | ★★（百毫秒~秒级/次，仅可点击时触发，不可实时） |
| 隐私 | ★★★★★（本地 ONNX+CoreML，零上传，AGPL 合规） |
| 工程量 | ★★（中大：转模型 + 推理流水线 + bbox 后处理 + 坐标系对齐） |
| 覆盖率 | ★★★★★（纯像素，Electron/Web/canvas 全覆盖） |

### 路线 C：混合（AX 优先 + 视觉/坐标兜底）★ 推荐

**原理**：点击发生时按代价从低到高逐级尝试，命中即止：

```
点击 (x,y)
  │
  ├─① AX hit-test：AXUIElementCopyElementAtPosition → 拿 AXFrame
  │     命中且矩形有效(非整窗口/非空 AXGroup) → 用真实控件矩形 ✅【原生应用，微秒级】
  │
  ├─② [可选/二期] 视觉检测：该帧跑 YOLOv8 Nano → 命中坐标的 bbox
  │     AX 空但视觉命中 → 用视觉 bbox ✅【Electron/Web 兜底】
  │
  └─③ 坐标兜底：都没有 → 退回现状(光标点 + 渲染层 Auto 跟随) ✅【永远不会更差】
```

> ★ **C 的精髓 = 渐进增强、永不退步**：最差情况退回 Cap 现有的成熟体验（光标跟随），任何一级命中都是净增益。且 ① 几乎零成本（权限/依赖都现成），可**先只做 ①+③ 上线**（一期），② 视觉作为二期增量——风险可控、价值可分期兑现。

| 维度 | 评价 |
|---|---|
| 精度 | ★★★★★（原生 AX 精确，Web 视觉兜底，永不低于现状） |
| 性能 | ★★★★（AX 微秒级覆盖多数；视觉仅在 AX 空时点击触发） |
| 隐私 | ★★★★★（全本地，AGPL 合规） |
| 工程量 | 一期(①+③) ★★★★ 小 / 二期(+②) ★★ 中 |
| 覆盖率 | ★★★★★（原生+Web+canvas 全场景） |

### Windows 侧对应能力（一笔带过，重点仍 macOS）

Windows 的等价物是 **UI Automation (UIA)**：`IUIAutomation::ElementFromPoint(POINT)` 反查坐标处元素，读 `CurrentBoundingRectangle`（RECT）+ `CurrentControlType`。Rust 侧用官方 `windows` crate（`Windows::UI::UIAutomation`）即可。

> 与 macOS AX 高度对称：同样"坐标→元素矩形"，同样有 Electron/Chromium 盲区（Chromium 默认不建 UIA 树，需 `--force-renderer-accessibility`）。因此**路线 C 的混合架构可跨平台复用**——采集层抽象一个 `fn element_bounds_at(x,y) -> Option<Rect>` trait，macOS 实现走 AX、Windows 实现走 UIA，上层生成/渲染逻辑零差异。Cap 双平台优势在此延续（Screen Studio 仅 macOS，官方确认 Windows 永不做）。Windows 实现建议放在一期之后的独立增量，不阻塞 macOS MVP。

## 3. 与现有点击聚类算法的衔接点（关键，眼见为实）

现有自动聚焦链路（核对源码）：

```
录制采集            生成分段(P0已升级)                    渲染插值
cursor.rs    →     recording.rs 生成算法          →      zoom_focus_interpolation.rs
clicks/moves       place_clicks→时空聚类→ZoomSegment       ZoomMode::Auto 跟随光标算焦点
                   全程 mode=Auto, 不定坐标
```

### 衔接点 ①（采集层）：`crates/recording/src/cursor.rs` L314-331

16ms 采集循环里检测到 `pressed != prev`（点击翻转）处，正是 `CursorClickEvent` 入队的地方：

```rust
// 现状 L323-330
let mouse_event = CursorClickEvent { down: pressed, ..., time_ms: elapsed };
response.clicks.push(mouse_event);
// 语义缩放注入点：当 down==true 时，调 AXUIElementCopyElementAtPosition(屏幕绝对坐标)
//   → 拿 AXFrame(CGRect) → 归一化到 display+crop 同 CursorMoveEvent 的坐标系
//   → 附加为 CursorClickEvent 的新可选字段 element_rect: Option<XY 矩形>
```

> 必须在**采集时（点击当下）**取元素矩形——因为 AX 反映**实时** UI 状态，录制结束后控件可能已消失/变化，事后无法补取。这是 A/C 路线的硬约束。

### 衔接点 ②（数据结构）：`crates/project/src/configuration.rs`

- `CursorClickEvent` 加可选字段 `element_bounds: Option<ElementRect>`（serde 默认 None，**向后兼容旧录制**）。
- `ZoomSegment` 已有 `mode: ZoomMode { Auto, Manual{x,y} }`。语义矩形有两种落地法：
  - **方案甲（小改）**：扩展 `ZoomMode::Auto` 的语义——生成算法把簇内点击的 `element_bounds` 并集中心写入，渲染层 Auto 优先用它而非光标。
  - **方案乙（更彻底）**：新增 `ZoomMode::Element { rect }`，渲染层据矩形直接定位+定缩放强度（强度可由矩形大小反推：小控件放大多，大区域放大少）。

### 衔接点 ③（生成算法）：`recording.rs` L3206 `place_clicks`

现在 `place_clicks` 给每个点击插值**光标坐标**。语义版改为：优先用该点击的 `element_bounds` 矩形中心 + 尺寸，无矩形时退回光标插值（即路线 C 的 ③ 兜底）。聚类逻辑（时空双阈值）完全复用，只是"点"升级为"带矩形的点"，`dynamic_amount` 可进一步结合控件尺寸优化强度。

> **结论：衔接极干净**。三个注入点都是"加可选字段 + 优先用新字段、缺失则走原逻辑"，**不破坏现有任何路径**，旧录制照常工作。这正是前任 P0 算法"生成定时机、渲染定坐标"分层设计带来的红利——语义矩形可以无缝插进"坐标"这一层。

## 4. 工作量评估（分阶段）

| 阶段 | 范围 | 人日 | 风险 | 依赖/权限 |
|---|---|:---:|:---:|---|
| **一期 · 纯 AX(①+③)** | cursor.rs 采集元素矩形 + CursorClickEvent 加字段 + place_clicks 消费 + 渲染层用矩形中心 + 单测 | **3-5** | 低 | **零新增**（权限+依赖都现成） |
| 二期 · 矩形渲染增强 | `ZoomMode::Element` + 渲染层据矩形定位定强度 + 调参 UI（与设计师协作） | 3-4 | 中 | 无 |
| 三期 · 视觉兜底(②) | YOLOv8 Nano 转 ONNX + 复用现有 `ort`/CoreML + 点击帧推理 + bbox 坐标对齐 + AX 空时降级 | 5-8 | 中高 | 复用现成 `ort`，新增模型文件(~10MB) |

**MVP 建议（性价比最高）**：先做**一期纯 AX**。理由：
1. 零新增权限、零新增依赖、不碰渲染管线核心，可独立工程验证（绕开 Cap 整包卡 Xcode 的老问题）。
2. 在原生应用（系统设置/访达/原生工具类教程）上立刻可见"缩放框精准贴合控件"的差异化效果。
3. AX 空时自动退回现状，**永不退步**，可安全灰度。
4. 视觉兜底(三期)作为 Electron/Web 场景的增量，待一期验证价值后再投入。
