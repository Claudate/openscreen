## 0. 一句话结论（给决策层）

**Cap 的"自动聚焦"框架五脏俱全（采集→生成→渲染→开关→UI 全链路已通），真正的差距只在一个函数——自动生成算法是「能用级 MVP」（写死 2x 缩放、忽略移动轨迹、不定位点击坐标、一刀切合并）。这正是 Cap 被外部评测定级 `Limited zoom`、而 Screen Studio 卖 $200 的根因，也是我们用最小改动撬动最大差异化的支点。**

## 1. 自动聚焦链路（最关键）

### 1.1 录制时的数据采集 —— 底子非常扎实

文件：`crates/recording/src/cursor.rs`

- `spawn_cursor_recorder` 起一个 actor，**16ms 轮询（≈60Hz）** 采集三类事件：
  - `CursorMoveEvent`：位置变化才记录（带归一化坐标 x/y + `time_ms`）
  - `CursorClickEvent`：鼠标按键状态翻转才记录（带 `down` / `cursor_num` / **精确 `time_ms`**）
  - `KeyPressEvent`：按下/抬起都记录（带 keycode，可用于键盘浮层）
- 每 **5s 增量 flush** 到磁盘（`cursor.json` / `keyboard.json`），录制结束最终再 flush 一次，崩溃可恢复（`recovery.rs`）。
- 光标图像按 SHA256 去重存 `cursor_N.png`，含 hotspot、形状识别（macOS `NSCursor` / Windows `GetCursorInfo`）。

> **判断**：点击事件带精确时间戳，是"录完自动生成聚焦片段"的完美原料，**数据层零缺口**。

### 1.2 ZoomSegment 与 Auto 模式的真相

文件：`crates/project/src/configuration.rs`（L643-675）

```rust
pub struct ZoomSegment { start, end, amount, mode: ZoomMode, glide_*, instant_animation, edge_snap_ratio }
pub enum ZoomMode { Auto, Manual { x, y } }
```

- `ZoomMode::Auto` **不是**"自动生成片段"，而是**渲染时放大中心点的跟随模式**（Auto=跟随光标算中心，Manual=固定坐标）。
- `ZoomSegment` 的 start/end/amount **必须先存在**，由谁生成是另一回事 → 见 1.3。

### 1.3 ★ 关键纠偏：Cap **已有**「录完自动生成聚焦片段」能力（两条路都有）

| 路径 | 入口 | 触发方式 | 说明 |
|---|---|---|---|
| **录制结束全自动** | `recording.rs` → `project_config_from_recording` (L3265) | 设置项 `auto_zoom_on_clicks` 开启时**录完即自动生成** | `general_settings.rs`：serde 默认 `default_true`，构造默认 `false`（实际偏向默认开） |
| **编辑器一键生成** | 前端 `ZoomTrack.tsx` (L86) `generateZoomSegmentsFromClicks()` | 用户在时间轴点按钮手动触发 | 依赖 `meta().hasRecordedCursorData` |

> **纠偏**：产品经理初判"Cap 只有手动关键帧、缺录完自动生成"**不准确**。Cap 录完全自动 + 编辑器手动生成**两条路都已存在**。真正的瓶颈是下面的**生成算法质量**。

### 1.4 ★★ 核心瓶颈：生成算法 `generate_zoom_segments_from_clicks_impl`

文件：`apps/desktop/src-tauri/src/recording.rs`（L3071-3147）

**现算法逻辑**：每次点击 → 区间 `[click-300ms, click+2500ms]` → 间隔<2500ms 的区间合并 → 每段输出 `ZoomSegment { amount: 2.0(写死), mode: Auto }`。

**逐条对标 Screen Studio 的缺陷（= 差异化机会）**：

| 维度 | Cap 现状 | Screen Studio | 缺口性质 | 改造优先级 |
|---|---|---|---|:---:|
| 缩放强度 | `AUTO_ZOOM_AMOUNT = 2.0` **硬编码** | 按点击密集度/内容动态 | 算法太粗 | P0 |
| 触发依据 | **只看 clicks**，`_moves` 参数**被弃用**(下划线) | 点击+移动轨迹+停留 | 信息浪费 | P0 |
| 缩放中心 | 生成阶段**不定位点击坐标**，全交给渲染时跟随 | 精确定位每次点击位置 | 不够准 | P0 |
| 防抖/聚类 | 固定 `MERGE_GAP=2500ms` 一刀切 | 智能聚类(DBSCAN 类) | 策略僵硬 | P0 |
| 缓动/速度 | `glide/instant` 全用默认值 | 每段可调速度曲线 | 无智能 | P1 |
| 场景感知 | **完全不感知**滚动、打字、拖拽 | 区分场景切换 | 维度缺失 | P1 |

> **架构师建议**：差异化主战场 = **替换/增强这一个 `_impl` 函数**（纯 Rust，单点改动，AGPL 内闭环）。把"能用"拉到"Pro 级"：①引入移动轨迹+停留时长 ②点击聚类(密度自适应) ③逐段定位 Manual 坐标或精修 Auto 中心 ④缩放强度按区域内容动态 ⑤暴露调参（强度/速度/防抖）给 UI（设计师的调参面板正好对接）。

### 1.5 渲染算法 —— 已是 Screen Studio 级，无需重造

文件：`crates/rendering/src/zoom.rs`（弹簧物理）、`zoom_focus_interpolation.rs`、`cursor_interpolation.rs`、`spring_mass_damper.rs`

- `spring_ease` 弹簧动画（刚度200/阻尼40/质量2.25），`spring_ease_out` 出场更柔
- `calculate_follow_center` 跟随中心 + `edge_snap_ratio` 边缘吸附
- `ensure_cursor_visible` / `_gentle` 双重防出界（带 12%/15% 安全边距）
- 支持 `instant_animation` 瞬切、段间平滑过渡（含 gap 插值）、完整单元测试覆盖

> **判断**：渲染层是项目最成熟的部分，**只消费 ZoomSegment 不生成**。我们的改造**不碰渲染**，只升级生成。

## 3. 编辑器渲染管线扩展点

文件：`crates/rendering/src/layers/mod.rs` + `composite_frame.rs` + `frame_pipeline.rs`

**分层渲染管线（每种视觉效果 = 一个独立 layer 模块）**：
```
background → blur → display → cursor → camera → mask → text → captions → keyboard
```

| 想加的效果 | 扩展位 | 现状 |
|---|---|---|
| 光标平滑 | `cursor_interpolation.rs` + `CursorConfiguration`(tension/mass/friction 预设) | ✅ 已有，可调参增强 |
| 点击特效 | `ClickSpringConfig`(configuration.rs L463) + cursor layer | ✅ 弹簧已有，可加水波/高亮 |
| 键盘按键显示 | `keyboard.rs` layer + `KeyboardSettings` | ✅ 已有完整 layer |
| 运动模糊 | `screen_motion_blur` / `cursor.motion_blur` | ✅ 字段已有 |
| 新自定义效果 | **新增 layer 模块 + mod.rs 注册一行** | 扩展成本低 |

> **判断**：渲染管线是教科书级**可插拔分层架构**。加新效果 = 新增 layer 文件 + 注册，**不破坏现有管线**。光标/点击/键盘三大特效的扩展位都已铺好。

## 4. AGPLv3 合规边界

文件：`LICENSE`（头部声明）+ `licenses/LICENSE-MIT`

| 范围 | 许可 | 商业化含义 |
|---|---|---|
| `cap-camera*` / `scap-*` 系列 crate | **MIT** | 宽松，可闭源、可商用、可二次封装 |
| **其余全部**（desktop app / rendering / recording / editor / project / web…） | **AGPLv3** | 强 copyleft：**改动需开源，且"通过网络提供服务"也触发开源义务** |

**合规结论（结合产品经理变现方案）**：

| 做法 | 是否合规 | 说明 |
|---|:---:|---|
| 改 Rust 核心（含自动聚焦算法）做更强桌面版 | ✅ 但**须开源** | AGPL 改动必须开源；可作为"开源 Pro"提升口碑 |
| 闭源卖断整个 App | ❌ 违反 AGPL | 产品经理判断正确，不可行 |
| **独立增值云服务**（AI 用量、模板市场、团队空间） | ✅ 关键策略 | 新建独立服务/独立仓库，**不修改 AGPL 代码本体**，通过 API 对接即可闭源 |
| 桌面商用许可（约束官方分发二进制） | ✅ | 许可只约束官方编译的二进制分发，AGPL 下合法（Cap 现行做法） |
| MIT 部分（相机/采集）单独闭源封装 | ✅ | MIT 允许 |

> **架构师强调**：自动聚焦算法改进若直接改 `recording.rs`，**必须开源**——但这反而能强化"最强开源自动聚焦"的口碑卡位。**真正闭源护城河应放在"独立增值服务层"**（云 AI 编排、模板市场后端、企业管控），与 AGPL 代码用 API 解耦。

## 5. 给团队的协作输入

- **@产品经理**：纠偏一处——Cap **已有**录完自动生成 zoom（`auto_zoom_on_clicks`）+ 编辑器一键生成，**不是"只有手动关键帧"**。P0 应改写为"**升级自动生成算法质量**"（现算法写死2x/忽略轨迹/不定位坐标），而非"从零做自动生成"。这让 P0 工作量与风险都大幅下降。
- **@设计师**：自动缩放调参面板（强度/速度曲线/防抖阈值）**有明确后端落点**——`ZoomSegment` 已有 amount/glide_speed/edge_snap_ratio/instant_animation 等可调字段，UI 调参可直连。键盘浮层(`KeyboardSettings`)、点击特效(`ClickSpringConfig`)字段也已就绪。
- **@主控**：技术可行性结论 = **绿灯**。差异化命门是单点算法升级（`generate_zoom_segments_from_clicks_impl`），AGPL 下闭环；变现护城河放在独立增值服务层。建议下一步进入 P0 自动聚焦增强的详细技术方案设计。
